# System Prompt / Состояние и правила разработки Mod Load Order Sorter

Этот документ описывает экспериментальную версию мода и служит контекстом для дальнейшей разработки. Он не является отдельной задачей на реализацию всех перечисленных возможностей. При противоречии с текущим кодом сначала изучи код и уточни поведение; не считай закомментированные фрагменты работающим функционалом.

Снимок ниже описывает ветку после упрощения слоёв: слой — одна функция `load(ctx)`, которую менеджер выполняет в корутине; зависимостей между слоями нет. Тестирование в Project Zomboid с ZombieBuddy не выполнялось; наличие кода не доказывает работоспособность функции в игре.

## 1. Назначение и ограничения

**Mod Load Order Sorter [b42] - Experimental - NEW** расширяет `ModSelector.ModLoadOrderPanel`: добавляет инструменты ручного управления списком, анализ метаданных и Lua-файлов активных модов, пользовательские правила и топологическую сортировку. Сортировка и анализ конфликтов эвристические: они не гарантируют отсутствие проблем. Изменение состава и порядка модов существующего сохранения может повредить его — пользователю рекомендуется делать резервную копию сохранения.

- Целевая среда — Project Zomboid Build 42 и Kahlua/Lua 5.1. В Lua не используй `io.*`, `os.*`, `debug.*` и `ZomboidFileSystem`. Не используй `next()`: для проверки пустой таблицы применяй `utils:tableIsEmpty`.
- Lua читает и записывает файлы через доступные PZ API (`getFileReader`, `getFileWriter`, `getModFileReader`, `cacheFileExists` и др.). Фоновую работу Lua в главном меню выполняй через `Events.OnFETick` либо UI `update`/`prerender`, а не `Events.OnTick`.
- Обычный режим использует `getLoadedLuaCount()`/`getLoadedLua()` и PZ API; Java-мост ZombieBuddy — отдельное необязательное расширение, а не обязательная зависимость мода. Его файловый ввод-вывод в Java намеренно использует NIO и не добавляет Lua доступ к `io.*`.
- Перед изменениями изучай существующие модули и их API. Переиспользуй `ScrollExtensions.lua`, `ContextMenu.lua` и `WarningPopup.lua`. Не включай намеренно закомментированные вызовы и отладочные функции без отдельной просьбы пользователя.
- Во время редактирования спискового правила в редакторе клики по трём правым спискам должны игнорироваться, включая изменение выделения и навигацию.

## 3. Данные и слои

### Core и LayerManager

`Core.lua` создаёт `MLOS_CORE`, держит `core.layers`, категории, `COLORS`, `getColosLegendTooltip()` и функции чтения/записи секционных текстовых файлов. Конфигурация категорий хранится в `Zomboid/Lua/ModLoadOrderSorter/categoriesConfig.txt`; фиксированный порядок категорий:

`coreRequirement → tweaks → resource → map → vehicle → code → weapon → clothes → items → ui → other → translation → undefined`.

Конфиг позволяет менять сопоставления тегов/флагов; код сбрасывает порядок категорий к стандартному. `1_Utils.lua` содержит в том числе `deepCopy`, `MergeTablesDedup`, `tableIsEmpty`, `getElementIndex` и его алиас `indexOf`.

`LayerManager.lua` — единственный файл жизненного цикла (отдельных `LayerRun.lua` и `TickScheduler.lua` больше нет). При загрузке он регистрирует слои в порядке `sortingRules → modInfo → modFiles`; новый слой добавляется одним вызовом `manager:registerLayer(name, layer)` с уже загруженным модулем. Модуль без `load` регистрируется как заведомо падающий слой, чтобы ошибка была видна в UI и не ломала остальные.

`initialise(modsList, { reread, onProgress, onComplete })` делает снимок списка, создаёт по корутине на слой и вешает один обработчик `Events.OnFETick`. Слои выполняются **по очереди в порядке регистрации**; за тик расходуется не больше `FRAME_BUDGET_MS` (8 мс). Обработчик снимается, когда закончился последний слой. Состояние запуска хранится в объекте запуска, а не в полях слоя.

Контракт слоя:
- Слой — таблица с `load(self, ctx)` и данными в `self.data`. Возврат из `load` означает готовность, `error()` — ошибку слоя; отдельных `complete`/`fail` нет. Ошибка одного слоя не останавливает следующие, но запуск считается неуспешным.
- `ctx.mods` — снимок `modList.items`, `ctx.reread` — запрос перечитывания. `ctx:step(current, total)` обновляет прогресс и уступает управление, если бюджет кадра исчерпан; вызывай его после каждой единицы работы. `ctx:wait()` уступает управление до следующего тика — так ожидают внешний результат (ответ Steam, Java-задачу) в обычном цикле `while not done do ctx:wait() end`.
- **Не вызывай `ctx:step`/`ctx:wait` внутри `pcall`** (и внутри функций, вызываемых из Java, например компаратора `table.sort`): yield не проходит через такую границу ни в Lua 5.1, ни в Kahlua.
- Слой может читать `core.layers.<имя>.data` слоёв, зарегистрированных раньше него. Сейчас слои друг от друга не зависят: слои хранят только факты о модах, а всё, что комбинирует несколько слоёв (граф, несовместимости, эффективная категория, валидация), находится в `2_SortingCore.lua`.
- Отмена: `manager:cancel()` или повторный `initialise` снимают обработчик и больше не возобновляют корутины старого запуска, поэтому его поздние внешние callback-и ни на что не влияют. Необязательный `layer:cancel()` вызывается для прерванного или упавшего слоя и освобождает внешние ресурсы (Java-задачу). Необязательный `layer:getWarnings()` возвращает список `{ severity, layer, title, message }`.
- Статусы слоя — `pending`, `running`, `loaded`, `failed`. `getStatus()` возвращает `{ total, finished, failed, progress, completed, success, layers = { { name, status, error, progress = { current, total } } } }`; `isCompleted()` — все слои завершились (в том числе с ошибкой), `isSuccessful()` — без ошибок. `loaded` означает готовность **самого слоя**, а не отсутствие частичных проблем в данных отдельного мода. `getWarnings()` собирает предупреждения загруженных слоёв и по одной записи `CRITICAL` на каждый упавший. Сортировка и редактор не запускаются до успешного завершения анализа.

### ModsInfo

`ModsInfo:load(ctx)` обрабатывает активный список и не зависит от правил сортировки. `getExtraModInfo` объединяет данные `ChooseGameInfo.Mod` и `mod.info`: имя, ID, категорию, теги/флаги, `require`, `loadAfter`, `loadBefore`, несовместимости и карты; результат кэшируется по `modId` до `reread`. Слой вычисляет обратные зависимости `requiredBy` и не включённые требования `warnings.missing` (по ним строится `getWarnings`). Данные модов, которых нет в текущем запросе, удаляются. Теги/флаги сопоставляются с конфигурацией категорий; пользовательская категория, позиции `loadFirst`/`loadLast` и несовместимости из правил учитываются только сортировщиком. Предупреждения о включённых несовместимых модах (из `mod.info` и из правил) выдаёт `sortingCore:getIncompatibleWarnings(modsList, rules)`; панель показывает их после успешной загрузки слоёв и после сортировки.

### SortingRules

`SortingRules.lua` читает/пишет `Zomboid/Lua/ModLoadOrderSorter/sorting_rules.txt`, при отсутствии нового файла поддерживает перенос старого файла. Данные индексируются по `modId` и включают `loadAfter`, `loadBefore`, `incompatibleMods`, `category`, `loadFirst`, `loadLast`. Последние два имеют значения `off`, `on`, `category` и взаимоисключаются при `setPosition`.

`SortingRules:load(ctx)` вызывает `ensureData(ctx.reread)`: файл читается один раз за сессию Lua (флаг `cacheLoaded`) или при `reread`. `beginEdit` создаёт глубокие копии сохранённых и рабочих правил; `discardEdit` откатывает рабочую копию; `commitEdit` сохраняет её в файл. Симуляция использует рабочие правила без записи.

### ModsFiles и кэш

`ModsFiles.lua` собирает относительные пути Lua-файлов, а `ModsFilesParser.lua` анализирует определения/переопределения функций, локальные алиасы и предполагаемые хуки. Парсер не зависит от API игры: ему передаётся объект с `readLine()`/`close()` (игровой reader или `Parser.stringReader(text)`); поддерживаются однострочные комментарии и `--[[ ... ]]`. Это эвристический парсер, а не полноценный синтаксический анализатор Lua: длинные комментарии с `=` и строки с маркерами комментариев могут обрабатываться неверно.

Данные мода содержат `rootDir`, массив `files` (также индексируемый по пути для списка целей), `modifications`, `signature`, `complete` и, при Java-анализе, `fsSignature`. Запись `modifications` содержит файл, полную цель, имя таблицы/метода, строку, признак хука и необязательный алиас.

Общий кэш — `Zomboid/Lua/ModLoadOrderSorter/modsFilesCache.txt`, с секциями по `modId` и строками `signature`, `complete`, `files`, `mod`, необязательной `fssignature`. Сигнатура включает `version` из `mod.info`, количество файлов, возвращаемое PZ API, и при наличии время обновления Workshop. Steam-запрос асинхронный: слой ждёт ответ в своей корутине не дольше `STEAM_TIMEOUT_MS` (30 с), затем использует fallback; при неудаче код сохраняет предыдущую временную метку из кэша. Учитывай ограничения и неполноту PZ API перечисления файлов; не считай сигнатуру полной проверкой содержимого.

Весь слой — один конвейер `ModsFiles:load(ctx)`: чтение кэша → `fetchWorkshopTimes(ctx)` → для каждого мода `scanMod` → сохранение кэша. Режимы различаются только источником списка файлов и текста:

- **Без загруженного Java-моста (`scanLoaded`):** список файлов берётся из загруженных в этой сессии Lua-файлов (`getLoadedLua`), содержимое читается `getModFileReader`. Для незагруженных модов остаются данные кэша; мод попадает в `notLoaded`, чтобы предупредить о возможной необходимости перезапуска. `listFilesInModDirectory` в игре не рекурсивна и возвращает только имена файлов непосредственно в указанной папке, поэтому для незагруженного мода список `media/lua` обычно пуст и такой мод считается «без Lua-файлов».
- **С доступным мостом (`openBuddySnapshot` + `scanSnapshot`):** моды обрабатываются по одному, слой ждёт Java-задачу через `ctx:wait()`. Мост перечисляет `.lua` в `common` и версионной папке, при совпадении путей приоритет у версионной папки. SHA-256 содержимого и путей помогает инвалидировать кэш даже при неизменном числе файлов. Старый кэш может использоваться при совпадении стандартной сигнатуры и списка файлов. Если мост для конкретного мода вернул ошибку, некорректный результат или не смог отдать файл, для этого мода выполняется `scanLoaded` с признаком `bridgeFailed`: результат всегда помечается неполным и попадает в `notLoaded`; остальные моды продолжают обрабатываться через мост. Отмена или ошибка слоя освобождает Java-задачу (`layer:cancel()`).
- Java получает пути только через реестр модов игры, читает файлы в daemon-потоке, не следует симлинкам внутри `media/lua` и ограничивает размер: 16 МиБ на файл, 128 МиБ на мод. Для первой загрузки/обновления JAR может понадобиться перезапуск и разрешение ZombieBuddy. Если агент или мост недоступны, должен сохраняться обычный режим и чтение общего кэша.

## 4. Сортировка и валидация

`Core/2_SortingCore.lua` строит ориентированный граф активных модов. Рёбра имеют веса: `require` 100, `loadAfter`/`loadBefore` из mod.info 95, пользовательские правила 90, полная перезапись перед хуком 50, сохранение порядка одинаковых файлов 10, другие эвристические подсказки порядка целей 5. Результаты неполного анализа модификаций не используются для эвристики функций.

Эффективные категории зависимостей повышаются по явным рёбрам до устойчивого состояния. Алгоритм Кана выбирает доступные узлы по глобальной позиции, категории, положению в категории и имени. В цикле разрывается слабейшее ребро, действительно входящее в цикл, и формируется предупреждение; при цикле из одних жёстких рёбер может быть разорвано и жёсткое. Одновременные полные перезаписи одной цели и несовместимые моды также могут давать предупреждения.

`validate` возвращает статусы по modId с приоритетом **purple > red > yellow**:
- `purple` — активная несовместимость;
- `red` — отсутствующая или загружающаяся позже обязательная зависимость;
- `yellow` — нарушение мягкого правила, позиции или порядка категорий;
- отсутствие статуса — нарушение не обнаружено.

`applyOrder` записывает прежний порядок в `ModLoadOrderSorter/loadOrderBackup.txt` и перестраивает `panel.modList.items`; это резервная копия **порядка**, а не игрового сохранения, и автоматического восстановления сохранения она не обеспечивает.

## 5. Интерфейс

`MLOS_ModSelector_overrides.lua` расширяет панель порядка: увеличивает её, подключает поиск, мультивыбор, кнопки перемещения и автопрокрутку при перетаскивании, контекстное меню, правый список файлов с поиском и чекбоксом конфликтов, индикатор прогресса всех слоёв с активными задачами, `WarningPopup`, кнопку редактора правил, справку цветов и информационный тултип. `autoSort` вызывает сортировщик и применение порядка. `fixMissingModsCrash` отключает недоступные моды, а `fixBackButtonJoypadFocus` обрабатывает выход и подтверждение изменений.

`ScrollExtensions.lua` — общая реализация перечисленных инструментов; `ContextMenu.lua` рисует меню; `WarningPopup.lua` показывает критические/обычные сообщения, позволяет копировать отдельные сообщения или все сразу и показывает `copiedFlash`. `FolderSupport.lua` реализует папки как представление содержимого списка (создание, переименование, удаление, перенос, сворачивание и раскрытие совпадений поиска), не меняя порядок модов; подключение к файловому инспектору сейчас закомментировано.

`SortingRulesEditor.lua` содержит три колонки: список модов с поиском, кнопки режимов `loadAfter`/`loadBefore`/`incompatibleMods` и комбобоксы категории/позиции, справа — цели правила, `Required` и `Required By`. Во время режима редактирования выбираются цели во временный список; Apply переносит его в рабочую копию, Cancel и повторное нажатие режима отменяют. Правые списки во время режима не обрабатывают клики. Кнопки внизу — выход без сохранения, симуляция и сохранение с выходом. UI-часть и её связи с владельцем следует проверять в игре, а не считать полностью проверенными.

`core.COLORS` — общая палитра и легенда. Отдельного `ColorLegend.lua` после рефакторинга нет. В коде присутствуют `MLOS_refresh` и `MLOS_updateView` для статусов, списка файлов, конфликтов и подсказок, но их текущее подключение и ограничения нужно учитывать (см. ниже).

## 6. Контракты при дальнейшей работе

1. Сохраняй существующий формат кэша и правил либо предусматривай обратную совместимость/миграцию. Не помечай неполный анализ успешным намеренно; в спорных ситуациях сохраняй предупреждение.
2. Обрабатывай только выбранные/активные моды, если пользователь явно не запросил индексирование всех установленных. Продолжительные операции не должны блокировать UI.
3. При добавлении слоя проверь его реальную регистрацию (`registerLayer` в `LayerManager.lua`), порядок, наличие `load(ctx)` и вызовы `ctx:step`/`ctx:wait` вне `pcall`; не считай файл в `modsSupport/` подключённым автоматически. Не добавляй в слой данные, зависящие от правил сортировки или текущего порядка, — им место в `2_SortingCore.lua`.
4. Сохраняй приоритет валидатора, транзакционность редактора и запрет кликов по правым спискам в режиме редактирования. Не смешивай рабочие и сохранённые правила.
5. Не утверждай, что сортировка исключает конфликты. Отличай резервную копию порядка от резервной копии игрового сохранения.
6. Не включай закомментированные функции, подключения UI или отладочные вызовы без отдельного указания пользователя.

## 7. Наблюдаемые ограничения после рефакторинга

Это наблюдения по коду, а не поручение исправлять их в любой новой задаче:

- В `ModLoadOrderPanel` вызовы `MLOS_refresh` после завершения первоначального анализа и автосортировки закомментированы; `render`, вызывающий `MLOS_updateView`, и создание `fileTooltip` также закомментированы. Обновление и тултипы инспектора поэтому не следует описывать как полностью подключённые. Существуют другие вызовы `MLOS_refresh`, например из фильтра и повторного сканирования.
- `validate` возвращает имена `purple`, `red`, `yellow`, а `MLOS_refresh` индексирует ими `core.COLORS`, где ключи называются `incompatible`, `requirementsError`, `sortingRulesWarning`. При текущем коде для этих статусов выбирается `reset`; цветовая подсветка панели требует проверки и согласования. В редакторе используется отдельная локальная таблица цветов.
- `FolderSupport` не подключён к правому списку панели: вызов `addFoldersSupport` закомментирован. `ModManager_ModListData.lua` — задел, не зарегистрированный рабочий слой.
- Эвристический парсер и обычная сигнатура не гарантируют обнаружения всех изменений и конфликтов.
- `editor_interaction.lua` и `folders_and_popup.lua` используют моки, не соответствующие текущим зависимостям/палитре после рефакторинга UI. Их необходимо адаптировать при работе с соответствующими частями; не считать весь набор тестов зелёным.

## 8. Проверка изменений

- При изменении Lua проверяй синтаксис и тесты именно в Lua 5.1/Kahlua-совместимой среде. При отсутствии системного Lua можно использовать Python `lupa.lua51`; обычный `lupa.LuaRuntime` может использовать другую версию Lua. Тесты находятся в `tests/`: `layer_manager.lua` проверяет жизненный цикл на слоях-заглушках (очерёдность, бюджет кадра, ожидание, ошибки, отмену), `layer_integration.lua` — реальные слои с моками PZ, `smart_sorter.lua` и `zombie_buddy_bridge.lua` — сортировку и чтение файлов/кэша. Слой можно запускать и без менеджера: достаточно корутины и `ctx` с `mods`, `reread`, `step`, `wait` (см. `start` в `smart_sorter.lua`). Тесты слоёв выставляют `_G.next=nil` и подменяют `getTimestampMs`. Для двух старых UI-тестов требуется обновление, описанное выше.
- Java-тест `tests/java/ModFilesBridgeTest.java` использует заглушку `ChooseGameInfo`; инструкции сборки моста — `java/mlos/README.md` и `java/mlos/build.sh`. Моки не заменяют проверку в игре с установленным и разрешённым ZombieBuddy.
- Проверяй JSON локализаций и `git diff --check`. При невозможности запустить игру явно указывай, что реальная UI/Java-интеграция не проверена.
